Scroll is the timeline.

Every scroll-animation library runs JavaScript sixty times a second to learn something the browser already knew. Dolly asks CSS instead — 16 camera moves, one attribute, no runtime. The counter up there is reading your scroll with no JavaScript either.

What it refuses to do.

the part that matters

It never hides your content.

Every other library in this category puts opacity: 0 in a base rule and reveals it from script. When the script fails, is blocked, or the browser lacks support, the page is blank. Dolly puts the hidden state only in @keyframes, so no support means didn't animate — never didn't appear.

It has no runtime to fail.

No IntersectionObserver, no scroll listener, no rAF loop, no init call, no provider, no hydration. Nothing runs, so nothing runs late. Dolly is a stylesheet, and a stylesheet is the whole product.

Reduced motion is a real path.

Under prefers-reduced-motion every move switches off and the page renders exactly as authored — because the authored state was never the hidden one. No suppression hack, no second stylesheet.

Firefox is fine, today.

Scroll timelines run in Chrome 115+, Edge, Safari 26+ and Opera — about 87% of the web, with Firefox landing in 159. Everyone else reads a complete, still page. That is the whole fallback; there is no shim to ship.

The entire API.

one attribute

Link the stylesheet, annotate existing markup. There is no init call, no wrapper component and no configuration object, because there is nothing running that could read one.

<!-- one link, then annotate markup you already have -->
<link rel="stylesheet" href="dolly.css">

<h1 data-dolly="tilt-up">Arrives as you reach it</h1>
<img data-dolly="rack" src="still.jpg" alt="">
<div data-dolly="progress" class="reading-bar"></div>

/* tune the range per element when the default is wrong */
<section data-dolly="crane" style="--dolly-range: entry 0% cover 60%" data-dolly-range>
